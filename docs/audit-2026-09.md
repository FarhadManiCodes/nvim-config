## Verified findings

### 1. `jupytext` is not installed — `.ipynb` opens as raw JSON (closed, expected)

The only finding with a user-visible consequence, and it is stated by the plugin's own
healthcheck:

```
jupytext: 1 ⚠️
- ⚠️ WARNING no jupytext found -- `.ipynb` will open as raw JSON (safe fallback, not a failure)
  - ADVICE:
    - Install it in the project venv, then `:restart`:
    - uv pip install jupytext         # the normal route here
    - uv tool install jupytext        # or everywhere, if you prefer
    - Looked in: $VIRTUAL_ENV/bin, <root>/.venv/bin, PATH
```

Confirmed absent everywhere it is looked for: not on `PATH`, not a `uv tool` (the only three
installed are `basedpyright`, `mathunicode`, `paper-refinery`), and no active venv.

**Closed 2026-09-09 — no action. The measurement was right and the premise was wrong.** This
finding compared against a uv-tool setup that had already been superseded:
`dotfiles/revisit.md:145` records the accepted decision as **jupytext installed per-venv, when
notebooks are actually needed**, not as a uv tool and not system-wide, matching how jupyter is
handled here generally. An empty `uv tool list` is therefore the *expected* state, not evidence
that something was removed and nothing noticed.

The user confirms notebooks open as markdown in a venv that does have jupytext, which is the
half that matters: resolution is venv-first per commit `5d33949` (*"resolve the CLI per notebook
open, not once at startup"*), so the CLI being absent outside such a venv is the designed safe
fallback. That is why `lua/jupytext/health.lua` reports it as a warning rather than an error —
and why this warning is permanent and should not be re-raised as a finding at the next audit.

### 2. `vim.validate{<table>}` is deprecated — breaks at Nvim 1.0 (fixed)

```
vim.deprecated: 1 ⚠️
- ⚠️ WARNING vim.validate{<table>} is deprecated. Feature will be removed in Nvim 1.0
  - ADVICE:
    - use vim.validate(<params>) instead.
    - stack traceback:
        ~/.local/share/nvim/lazy/jupytext.nvim/lua/jupytext/init.lua:163
```

**Third-party code, but fixable here — fixed 2026-09-09.** The traceback points inside
`jupytext.nvim`, not into `lua/`, and no upstream fix is coming: its last commit is 2024-04-05
and the pinned `c8baf3a` *is* `origin/HEAD`, so the plugin is unmaintained and this would have
become a hard failure at Nvim 1.0, taking notebook support with it.

`setup()` cannot simply be skipped — the read guard harvests its `BufReadCmd` callback out of
the autocmd registry precisely because `read_from_ipynb` is a local. So `lua/plugins/init.lua`
wraps the call, stubbing `vim.validate` for its duration and restoring it immediately after.
Both suppressed assertions only check that the three literals passed are a table and two
strings, so nothing that could fail is skipped. `:checkhealth vim.deprecated` now reports OK,
and a bad-type call still raises — verifying the real function is back.

### 4. `lazy-lock.json` carries an uncommitted plugin update

Two plugins moved on 2026-09-05 and the lockfile change is still uncommitted:

```
nvim-treesitter  427e9222 -> 41416e81
vimtex           b5ea5770 -> e3559875
```

This is the change `sysup` warns about — the lockfile lives in this submodule, so a sync leaves
a second git tree dirty. It settled after one run; verified that neither
`nvim --headless "+checkhealth"` nor a plain `nvim --headless +qa` mutates it any further.

> **That "settled after one run" claim did not hold — re-measured 2026-09-09.** The working tree
> now reads `nvim-treesitter 427e9222 -> 5cb0114e`, not the `41416e81` recorded above. `vimtex`
> matches. So the lockfile moved again in the four days after this was written, by something not
> yet identified — the two headless commands checked above are cleared, so it was a third path.
> Until that is known, this finding cannot be closed by inspection: the recorded target and the
> real one disagree, and `AGENTS.md` says a conflicting number stays unresolved when the original
> query is unavailable.

> **Committed on 2026-09-09 by the user's decision.** The unexplained second move stays an open
> question, but the state itself was verified before accepting it: a full `:checkhealth` that day
> reports `nvim-treesitter` OK, tree-sitter ABI 15, and every installed parser loading. Note that
> tracking the lockfile is what made the discrepancy visible at all — without a committed
> baseline there is nothing to diff an unaccounted-for move against.

**Resolved:** committed as `nvim-treesitter 427e9222 -> 5cb0114e`, `vimtex b5ea5770 -> e355987`.
What moved treesitter the second time is still unidentified; if it recurs, roll back with

```bash

```

  2026-09-09, just before that file was collapsed to an `@AGENTS.md` import.
- **Re-run the health check** exactly as `sysup` does:
  ```bash
  nvim --headless "+checkhealth" "+w! /tmp/health.txt" +qa
  awk '/^=+$/{getline s; sub(/:.*$/,"",s); next}
       $0 ~ "^- [^ ]+ WARNING " {sub("^- [^ ]+ WARNING ",""); print s ": " $0}' /tmp/health.txt
  ```
  The severity markers are emoji (`✅`/`⚠️`/`❌`), so match the word after them rather than the
  emoji itself. Section names come from the line under each `====` rule.
- The last full report `sysup` wrote is at `~/.local/state/sysup/nvim-health.txt`, and the
  warning set it compares against is `nvim-health-warnings` beside it. Deleting the latter
  forces the next run to list everything again.
- **Do not `Lazy! sync` while auditing** unless the intent is to change plugin state — it
  rewrites the lockfile and will mix an update into the audit diff.
